Browser performance is slower: TypeScript takes 2.00× Go’s time and Dart takes 3.56× on the measured five-document workload. Performance parity has not been achieved.

The reader now converts uploaded PDFs in a local TypeScript worker and imports the resulting EPUB through its existing storage flow. Both packages can also be used separately. The Dart worker compiles to JavaScript and has its own public browser client.

What the ports preserve

The five PDFs are the requested 43-page arXiv paper, Axler’s Linear Algebra Done Right (404 pages), Hefferon’s Linear Algebra (525), Think Python (244), and Calculus Made Easy (292). Their block text, block order, table coordinates and spans, header associations and normalized Markdown match Go. Nineteen synthetic Go fixtures also check structure and geometry.

The requested paper retains all 13 tables, including merged model headings and grouped row labels. Its structures match the Go version that recovered all 1,473 nonempty author-HTML cells. That paper was a development example; this result does not generalize to every table.

Fourteen selected math crops achieve a mean ink F1 of 99.96026317503747%, with all 14 above 99%, for both ports. The metric compares positioned glyph appearance with a one-pixel tolerance at 216 dpi. It does not evaluate semantic equations, reading order, or whole-book accuracy. TypeScript math results · Dart math results.

Fifteen of 16 PNG assets match Go’s decoded pixels exactly. One masked JPEG is decoded and re-encoded as PNG; generic decoder rounding changes some RGB values by at most 3/255 while preserving alpha. The report retains changed-pixel counts rather than claiming every raster image is bit-exact.

How it works

PDF bytes
  → bounded PDF syntax, xref and stream parser
  → original content interpreter and font readers
  → positioned spans, glyphs, paths and images
  → reading order, cleanup, headings, code, lists and tables
  → typed blocks, metadata, assets and warnings
  → Markdown, semantic HTML or EPUB

TypeScript and Dart each implement this pipeline independently. There is no Go runtime, WebAssembly wrapper, PDF.js, hosted extraction service, or call from one engine into the other. Dependencies provide generic compression, JPEG, hashing and XML functionality. Complex tables retain rowspan, colspan, scope and header associations. Math uses positioned glyph SVGs.

Workers keep extraction off the UI thread, copy input before transferring it, enforce deadlines and support cancellation. Limits bound objects, pages, decoded data, operations, spans, images and assets. The reader’s extraction notes preserve warnings and incomplete status. Extraction stays local; the resulting EPUB still uses the existing upload and sync service.

Validation and remaining limits

56 TypeScript tests and 46 Dart tests passed, along with TypeScript type checking, Dart analysis, browser worker compilation, standalone Dart package validation, the production web build, and Go tests/vet. CI runs the package tests and builds; benchmark reproduction is documented separately.

Review fixed shared image-buffer ownership and named inline-image color-space lengths. Two confirmed limitations inherited from Go remain: scaled/zero-width vector strokes can render incorrectly, and discarded or clipping paths can influence ruling-based table detection. These require shared algorithm changes and new score runs; this port preserves Go’s current behavior. Review dispositions.

OCR, JPEG2000, JBIG2, complete color management and semantic math are still unsupported. Some PDFs remain complete: false. The libraries do not claim perfect visual reconstruction, exhaustive PDF support, or a clean review.
