PDF extraction now runs on the client

The Reader · 11 October 2026 · Independent TypeScript and Dart engines

The browser uses the TypeScript worker. The Flutter mobile app uses the Dart package in a separate isolate. Both produce an EPUB for the existing reader. Go stays independently usable, and neither app calls its extraction service.

Timing scope matters

The simulator import took 3,745 ms, including extraction, EPUB generation, inspection and local storage. A 20 ms UI timer fired 185 times. The browser worker took 1,269.2 ms for extraction and EPUB generation with input already loaded. These are different measurement scopes; neither is a physical-phone benchmark or a Go speed comparison.

Accuracy remains exactly matched to Go

The previously completed pinned olmOCR run scored 30.33110936410476% for Go, native TypeScript, native Dart and both browser workers, with identical outcomes on all 8,413 checks. This is a category macro pass rate, not whole-book accuracy. This integration changes no extraction-core algorithms and does not establish a new market rank or improve that score.

Exact-score benchmark, speed measurements and limitations. OCR, semantic LaTeX, JPEG2000 and JBIG2 remain unsupported; existing warnings are preserved.

Validation and reproduction

Client checks cover network-free conversion, invalid/encrypted inputs, size limits, deadline termination, source preservation and temporary-file cleanup. The iOS integration test exercises the production import service, local book store and native reader. TypeScript package/import tests: 56 passed. Full mobile suite: 464 passed, seven pre-existing skips. Mobile static analysis passed. The Android debug build passed.

The broader mobile suite exposed an archive 4.4 compatibility issue in MOBI packaging: the encoder now sets deterministic timestamps directly instead of patching ZIP headers. CI's Flutter SDK pin now matches Dart 3.13 dependencies.
